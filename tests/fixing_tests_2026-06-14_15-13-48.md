## Bugs Fixed

### Bug 1 — `src/handlers/openai.ts`: non-2xx upstream errors thrown as plain `Error` → 500

**Root cause:**

```js
// Before (line ~245):
throw new Error(`OpenAI API error: ${response.status} ${errorText}`);
```

`handleOpenAIRequest` handled upstream non-2xx with a plain `new Error(...)`. The outer `try/catch`
in `src/index.ts` calls `createErrorResponse`:

```ts
if (error instanceof ClaudeProxyError) {
  responseStatus = error.status;   // propagates upstream status
} else {
  responseStatus = 500;            // plain Error → always 500
}
```

So all `01_endpoints/interactions` requests (TC201–TC205) that used `gemini-2.5-flash` (routed to
`openai-completions` upstream, returned 403 from `/v1/chat/completions` block) appeared as 500.

The streaming path had a separate problem: it returned a fake HTTP 200 wrapping the upstream error
inside an SSE frame. This made TC206 (streaming interactions) appear to pass as a false positive.

**Fix (`src/handlers/openai.ts`):**

Added `import { handleTargetApiError } from '../utils/errors.js';` and replaced both branches with
a single call:

```js
// After:
if (!response.ok) {
    const errorText = await response.text();
    activeLogger.error(requestId, `OpenAI API error: ${response.status} ${errorText}`);
    handleTargetApiError(response, 'OpenAI API', { url: targetUrl, upstreamBody: errorText });
}
```

`handleTargetApiError` throws `ClaudeProxyError` with the correct HTTP status, which the outer
catch propagates correctly. This matches the pattern already used in `src/handlers/gemini.ts`.

**Impact on run output:**
- TC201–TC205 `interactions`: 500 → 403 (proxy correctly reports the OpenAI upstream blocked `/v1/chat/completions`)
- TC206 `streaming interactions`: was 200 (false positive) — test assertion updated (see below)

### Bug 2 — `src/index.ts` + `src/handlers/gemini.ts`: `:countTokens` path unrouted → 500

**Root cause (TC311, TC312):**

`/v1beta/models/:model:countTokens` was not matched by any condition in the routing `if`-chain:

```ts
// Only checked generateContent and streamGenerateContent — countTokens missing:
(path.includes(':generateContent') || path.includes(':streamGenerateContent'))
```

The path fell through to `parseFixedRoute`, which threw `new Error("Unsupported fixed route: ...")`.
That plain Error reached the outer catch → 500.

**Three-part fix:**

**`src/index.ts` — outer routing condition (line ~604):**
```ts
// Before:
(path.includes(':generateContent') || path.includes(':streamGenerateContent'))

// After:
(path.includes(':generateContent') || path.includes(':streamGenerateContent') || path.includes(':countTokens'))
```

**`src/index.ts` — model-extraction regex (line ~638):**
```ts
// Before (only matched generateContent):
path.match(/\/(v1beta|v1)\/models\/([^:?]+):(stream)?[Gg]enerateContent/)

// After (also matches countTokens):
path.match(/\/(v1beta|v1)\/models\/([^:?]+):(stream)?(?:generateContent|streamGenerateContent|countTokens)/)
```

**`src/index.ts` — new `parseFixedRoute` branch 3a (before existing branch 3):**
```ts
if ((path.startsWith('/v1beta/models/') || path.startsWith('/v1/models/')) && path.includes(':countTokens')) {
  const modelId = ...;
  if (defaultMode === 'gemini-generatecontent' || defaultMode === 'gemini-interactions') {
    // Route to upstream Gemini countTokens endpoint
    return { targetUrl: `${defaultBaseUrl}/${apiVersion}/models/${modelId}:countTokens`, ... };
  } else {
    // Fallback: forward to /v1/messages/count_tokens (Claude token-counting handler)
    return { targetUrl: `${defaultBaseUrl}/v1/messages/count_tokens`, handlerType: 'token-counting', ... };
  }
}
```

**`src/index.ts` — composite routing block (line ~765):**
Added a matching `else if` branch for `:countTokens` paths in the per-candidate URL builder.

**`src/handlers/gemini.ts` — new `handleGeminiCountTokensRequest`:**

Added a thin passthrough handler that forwards the request body to the upstream `:countTokens`
endpoint and returns the raw JSON (containing `totalTokens`):

```ts
async function handleGeminiCountTokensRequest(request, targetUrl, authHeaders, ...): Promise<Response> {
    // No body conversion — Gemini countTokens accepts the same `contents` format directly
    const response = await fetch(targetUrl, { method: 'POST', headers: geminiHeaders, body: request.body });
    if (!response.ok) handleTargetApiError(response, 'Gemini API', ...);
    const responseText = await response.text();
    return new Response(responseText, { status: 200, headers: { 'Content-Type': 'application/json' } });
}
```

Wired into `handleGeminiRequest`:
```ts
} else if (path.includes(':countTokens')) {
    return handleGeminiCountTokensRequest(request, targetUrl, authHeaders, ...);
}
```

**Impact on run output:**
- TC311 `v1beta/:countTokens`: 500 → 401 (upstream auth error, correct — Bucket 1)
- TC312 `v1/:countTokens`: 500 → 401 (same)

## Test Fix — TC206 False Positive Corrected

**File:** `testcases/01_endpoints/interactions.test.js`

TC206 passed in run #6 only because the old streaming-error path returned HTTP 200 with an error
wrapped in an SSE frame. After the `openai.ts` fix, the correct upstream error status propagates,
so the previous assertion would fail.

```js
// Before (false positive — passed only due to error-wrapping SSE bug):
assert(response.status === 200, 'Streaming should return 200');
assert(response.eventCount > 0, 'Should have streaming events');

// After (correct — proxy must not crash; 4xx from upstream is expected without credentials):
assert(
  response.status < 500,
  `Streaming interactions should not cause a proxy internal error (got ${response.status})`
);
if (response.status === 200) {
  assert(response.eventCount > 0, 'Streaming 200 response should have events');
}
```
