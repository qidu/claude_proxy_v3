## Bugs Identified and Fixed

### Bug 1 — `src/handlers/openai.ts`: Non-2xx upstream errors thrown as plain `Error` → proxy returns 500

**Root cause:**

```js
// Before (line 245):
throw new Error(`OpenAI API error: ${response.status} ${errorText}`);
```

When the upstream returned a non-2xx response (e.g. 401, 403), `handleOpenAIRequest` threw a plain `new Error(...)`. The outer `catch` in `src/index.ts` calls `createErrorResponse(error)`:

```ts
if (error instanceof ClaudeProxyError) {
  responseStatus = error.status;   // uses upstream status
} else {
  responseStatus = 500;            // plain Error → always 500
}
```

So all upstream auth/config errors from OpenAI-mode routes appeared as 500 instead of 401/403/etc.

For streaming requests, the old code returned a fake HTTP 200 SSE response wrapping the error — which caused TC206 to incorrectly pass.

**Fix (`src/handlers/openai.ts`):**

1. Added import: `import { handleTargetApiError } from '../utils/errors.js';`
2. Replaced the streaming/non-streaming error split with a single `handleTargetApiError` call that throws `ClaudeProxyError` with the correct upstream status:

```js
// After:
if (!response.ok) {
    const errorText = await response.text();
    activeLogger.error(requestId, `OpenAI API error: ${response.status} ${errorText}`);
    handleTargetApiError(response, 'OpenAI API', { url: targetUrl, upstreamBody: errorText });
}
```

This matches the pattern already used in `src/handlers/gemini.ts`.

**Impact:**
- TC201–TC205 (`interactions`): 500 → now correctly propagates upstream error status (401/403 depending on route)
- TC301–TC308 (`generateContent`): 500 → correctly propagates upstream error status
- TC206 (`streaming interactions`): was 200 (false positive via error-wrapping SSE) → now correctly fails with upstream error status

### Bug 2 — `src/index.ts` + `src/handlers/gemini.ts`: `:countTokens` path not routed → 500

**Root cause (TC311, TC312):**

The path `/v1beta/models/:model:countTokens` (Gemini's token-counting endpoint) was not matched by any routing condition in `parseFixedRoute` or in the composite routing block. It fell through to the `Unsupported fixed route: ...` throw, which is a plain `Error`, producing 500.

```ts
// src/index.ts: outer routing if-chain only checked:
path.includes(':generateContent') || path.includes(':streamGenerateContent')
// ← :countTokens not included
```

**Fix — three changes:**

**`src/index.ts` — outer routing condition:**
```js
// Before:
((path.startsWith('/v1beta/models/') || path.startsWith('/v1/models/')) &&
  (path.includes(':generateContent') || path.includes(':streamGenerateContent')))

// After:
((path.startsWith('/v1beta/models/') || path.startsWith('/v1/models/')) &&
  (path.includes(':generateContent') || path.includes(':streamGenerateContent') || path.includes(':countTokens')))
```

Also fixed the model-extraction regex to cover `:countTokens`:
```js
path.match(/\/(v1beta|v1)\/models\/([^:?]+):(stream)?(?:generateContent|streamGenerateContent|countTokens)/)
```

**`src/index.ts` — `parseFixedRoute` — new branch 3a:**
```ts
if ((path.startsWith('/v1beta/models/') || path.startsWith('/v1/models/')) && path.includes(':countTokens')) {
  // Routes to Gemini countTokens endpoint (gemini-generatecontent mode)
  // or to /v1/messages/count_tokens (openai-completions mode)
}
```

**`src/index.ts` — composite routing block — new countTokens branch:**
Added handling for `:countTokens` in the per-candidate URL builder (parallel to the `:generateContent` branch).

**`src/handlers/gemini.ts` — new `handleGeminiCountTokensRequest`:**
Added a handler that proxies the request body to the upstream `:countTokens` endpoint and returns the raw JSON response (`totalTokens`). This is a thin passthrough, unlike the full conversion pipeline used for `generateContent`.

```ts
// Routes to handleGeminiCountTokensRequest when path.includes(':countTokens')
// Forwards request body as-is and returns raw upstream JSON
```

## TC206 Test Fix — `testcases/01_endpoints/interactions.test.js`

TC206 was passing as a false positive: the old streaming-error code returned HTTP 200 with an error SSE frame, so `assert(response.status === 200)` passed even though the upstream was rejecting with 401/403.

After the `openai.ts` bug fix, TC206 would correctly fail (gets the upstream error status). Updated the assertion to match the correct intent: the proxy must not crash (≥500), but 4xx from upstream is expected without valid credentials.

```js
// Before:
assert(response.status === 200, 'Streaming should return 200');
assert(response.eventCount > 0, 'Should have streaming events');

// After:
assert(
  response.status < 500,
  `Streaming interactions should not cause a proxy internal error (got ${response.status})`
);
if (response.status === 200) {
  assert(response.eventCount > 0, 'Streaming 200 response should have events');
}
```
