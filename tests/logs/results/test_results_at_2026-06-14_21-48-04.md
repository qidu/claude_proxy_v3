### Bucket 2 — `/v1/models` upstream 401: 3 failures (proxy auth header pass-through)

Three tests send `GET /v1/models` with `Authorization: Bearer sk-test-key` and receive 401 from upstream `api.qnaigc.com`:

- **TC909** (05_upstream_modes) — Models List
- **TC604** (06_integration) — Content-Type header on GET /v1/models
- **TC605** (06_integration) — Models List Endpoint

Proxy log confirms: `[req_…] [ERROR] Error: Invalid API Key` (the upstream's own error message). The proxy's `handleModelsRequest` forwards the client's `Authorization: Bearer sk-test-key` header verbatim to `https://api.qnaigc.com/v1/models`, and `api.qnaigc.com` rejects it because that key is the **proxy's** auth token, not a valid upstream key.

These tests passed in round 1 but regressed in rounds 2 and 3 — same config, same client key. Likely cause: round 1 received a cached 200 response from the models handler (300 s TTL on success only — `src/handlers/models.ts`), then the cache expired and the upstream now refuses the unknown key.

**Action — `fix source codes: PROBABLY NO, fix config: YES`.** The handler behavior (forwarding client auth to upstream) is conventional for many proxies and the tests explicitly assert that a valid proxy Bearer yields 200. The correct fix is upstream-side: configure an upstream API key that `handleModelsRequest` should use when calling `/v1/models`, either by:

1. Adding `default_api_key` to `[upstream]` and having `handleModelsRequest` prefer it over the client header, or
2. Adding a `[models.models_list]` block with explicit `base_url` + `api_key` and routing `/v1/models` through it instead of falling through to `default_base_url`.

Option 1 is one-line; option 2 mirrors how other endpoints already route. Either way the upstream 401 disappears once the proxy sends a key `api.qnaigc.com` actually accepts.
