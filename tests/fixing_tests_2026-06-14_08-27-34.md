### Bucket 2 — TC309 SSE event shape assertion (1 failure, `01_endpoints/generateContent`)

```
Error: Assertion failed: SSE events should be Gemini candidates chunks or typed events
```

**Root cause:** `testV1BetaStreamGenerateContentStreaming` (TC309) checked only
`firstEvent?.candidates || firstEvent?.type`. The `sendStreamingRequest` helper parses
both `event: <name>` lines (emitted as `{event: "..."}` with no `candidates`/`type`) and
`data: {...}` lines. When the v1beta Gemini SSE stream begins with an `event:` name line,
`response.events[0]` is `{event: "..."}`, which satisfies neither condition — even though
subsequent events contain `candidates`.

The companion test TC310 (v1 endpoint) passed because it only checks `eventCount > 0`
without asserting event shape.

**Fix:** Changed the assertion from checking only `firstEvent` to scanning the whole
`response.events` array for any event with `candidates` or `type`:

```js
// Before:
const firstEvent = response.events[0];
assert(
  firstEvent?.candidates || firstEvent?.type,
  'SSE events should be Gemini candidates chunks or typed events'
);

// After:
const hasCandidates = response.events.some(e => e.candidates);
const hasTyped = response.events.some(e => e.type);
assert(
  hasCandidates || hasTyped,
  'SSE stream should include at least one Gemini candidates chunk or typed event'
);
```

File: `testcases/01_endpoints/generateContent.test.js` (TC309).

### Bucket 3 — TC1110 safeModels 2-element array normalization (skip, `09_composite`)

```
(skipped: could not configure test alias — 400: "Invalid model entry for claude.codestrong")
```

**Root cause:** `testCompositeTotalTokenLimit413` (TC1110) built `safeModels` by stripping
`api_key` from the dashboard GET response. However, the dashboard GET returns 2-element
arrays `[model, base_url]` for model entries that have a `base_url`, but the PUT validator
only accepts 1-element (`[model]`) or 3-element (`[model, url, api_key]`) arrays (see TC1204).

The `[models.claude]` category contains `codestrong = ["code-strong", "", ""]`, which the
dashboard GET strips to `["code-strong", ""]` (a 2-element array with empty url). The PUT
with this 2-element array was correctly rejected by the validator, but this rejection was
unrelated to the 413 path being tested.

TC1211 and TC1214 solve the same problem by normalizing before PUT:
- `[model, url]` with non-empty url → `[model, url, ""]`
- `[model, ""]` → `[model]`

**Fix:** Added the same normalization to `testCompositeTotalTokenLimit413` so the models
payload round-trips cleanly through the validator. The test can now reach the PUT → first
request → 413 assertion path (if the upstream is reachable).

File: `testcases/09_composite/composite.test.js` (TC1110).
